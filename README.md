# scnet-stream

Music source separation with [SCNet](https://github.com/starrytong/SCNet) on Apple silicon, through
the Core ML export by [demixr](https://github.com/demixr/scnet-executorch), with memory that stays
flat however long the track is.

```sh
pip install git+https://github.com/supwick-hub/scnet-stream
scnet-stream track.m4a stems/
# stems/vocals.wav  stems/drums.wav  stems/bass.wav  stems/other.wav
```

```python
from scnet_stream import separate

paths = separate("track.m4a", "stems/", device="gpu", progress=lambda stage, f: print(stage, f))
```

macOS on Apple silicon, Python 3.10+, `ffmpeg` on `PATH`. Dependencies are NumPy and coremltools;
PyTorch is not needed.

**No model weights are included.** On first use the Core ML package is downloaded from the
[scnet-executorch v0.1.2 release](https://github.com/demixr/scnet-executorch/releases/tag/v0.1.2)
into `~/Library/Caches/scnet-stream` (or `$SCNET_STREAM_CACHE`), checked against a pinned SHA-256
and compiled once. See [Licensing](#licensing) before you use the weights for anything.

## What is different from a straightforward runner

SCNet separates a track in 7.8-second segments that overlap by 25%, each weighted by a triangle
and added into track-length accumulators. A direct port holds the whole decoded track, a
`(4 stems, 2 channels, length)` accumulator and several temporaries of the same size, so its
memory grows with the track. This package changes where the numbers live, not the numbers:

- **Streamed in, streamed out.** ffmpeg decodes a block at a time. The input is read twice — once
  for the mean and standard deviation SCNet normalises by, once through the network — rather than
  held. The accumulators are one segment long, and each stretch of output is written to the WAVs
  as soon as no later segment overlaps it.
- **The same output.** Segments, weights and float32 arithmetic are the same and in the same order,
  so the streamed stems are **bit-identical** to the whole-array loop on the same input
  (`tests/test_core.py`, at overlaps 0, 0.25 and 0.5, with a partial last segment).
- **No PyTorch.** The STFT, its inverse and the normalisation around the network are reimplemented
  in NumPy. Against the PyTorch versions the export was made with, the stems from the real model
  differ by 55–72 dB SNR per stem on a synthetic test signal — above the export's own agreement
  with PyTorch SCNet, previously measured at 45–58 dB.

### Memory

Peak `phys_footprint` of a fresh process (what Activity Monitor shows; it includes Core ML's GPU
buffers, which RSS does not), GPU, 25% overlap, synthetic AAC input generated by
`benchmarks/bench.py`, measured on an Apple M1 with 8 GB:

| track length | 1 min | 2 min | 4 min | 16 min | 60 min |
|---|---|---|---|---|---|
| **scnet-stream** | 579 MB | — | 582 MB | 582 MB | 583 MB |
| whole-track arrays, same model | 676 MB | 802 MB | 1,251 MB | not run | not run |

The whole-array runner (`benchmarks/bench.py whole`) grows by roughly 125–225 MB per minute of
audio, so a 16-minute track would need several GB; it was not run past 4 minutes to keep the test
machine out of swap. `tests/test_memory.py` checks the flat line without the model: 1 and 8
minutes of synthetic audio through a pass-through network must peak within 60 MB of each other
(measured: 259 MB and 268 MB).

### Where the time goes

The same 60-minute run: 621 s in all, about 5.8× realtime, on a machine that was not idle.

| | share |
|---|---|
| Core ML network (616 segments, ~0.84 s each) | 84% |
| inverse STFT | 8% |
| writing four 16-bit WAVs (the dither) | 3% |
| forward STFT and normalisation | 2.5% |
| first pass over the input (decode + statistics) | 1% |
| loading the compiled model | 0.6 s |

Almost all of it is the network, which is Core ML whatever language drives it. Two things set how
much network there is:

- **Overlap.** At 25% every sample passes through the network 1.33 times. `overlap=0.125` would cut
  network passes by about 14%, but changes the samples at every join; it is exposed as a parameter
  and has not been evaluated for quality. `overlap=0` is fastest and joins with no crossfade.
- **Compute units.** On an otherwise quiet M1, earlier measurements of the same model put a segment
  at about 0.67 s on the GPU, 0.58–0.61 s on the Neural Engine (9–13% faster) and 1.66 s on the CPU
  alone. Running GPU and Neural Engine side by side was *slower* (about 0.80 s a segment): they
  share memory bandwidth.

### The Neural Engine's one-time preparation

`device="ane"` works, but the first load of the model on the Neural Engine prepares it for that
chip, which took about 20 minutes (and around 1 GB) on an M1. macOS caches the result per compiled
model, under `~/Library/Caches`; later loads, including in fresh processes, take about 0.2 s. The
cache is not permanent — macOS may purge it and an OS update may invalidate it — and a different
compiled model pays the full preparation again. That is why the default is the GPU, which needs no
preparation. If you use the Neural Engine, warm it once ahead of time (for example
`scnet-stream --device ane` on a short file) rather than inside something time-sensitive.

### macOS: freed memory that stays counted

macOS's malloc keeps freed *large* blocks in a per-process cache, still dirty, and counts them in
the process's footprint. Allocating and freeing arrays of 60, 65, … 175 MB in turn left about
2.8 GB resident with nothing alive (macOS 26.2). A long-running process that frees a different-sized
large array per track grows to the sum of everything it has freed, not to its peak — which looks
exactly like a leak.

Setting `MallocLargeCache=0` in the environment turns the cache off. libmalloc reads it once, at
process start, so it has to be in the environment when the process starts:

```sh
MallocLargeCache=0 python my_batch_job.py
```

or, from inside a script, as early as possible (this re-execs the process once, same pid):

```python
from scnet_stream.macos import relaunch_without_large_malloc_cache
relaunch_without_large_malloc_cache()
```

The CLI does the same with `--no-malloc-large-cache`. Nothing does it automatically: scnet-stream's
own arrays are small and fixed in size, so a single separation does not need it; it matters for
hosts that also do whole-array work between separations. `scnet_stream.macos.footprint_bytes()` and
`peak_footprint_bytes()` read the same figure Activity Monitor shows.

## Usage

```
scnet-stream INPUT OUT_DIR [--device gpu|ane|cpu|all] [--overlap 0.25] [--float32]
                           [--model PATH] [--no-malloc-large-cache] [-q]
```

- `INPUT`: anything ffmpeg decodes; it is resampled to 44.1 kHz stereo. ffmpeg drops the encoder
  delay at the start of AAC and MP3 files, so the stems line up sample for sample with ffmpeg's
  decode of the input.
- Output: `vocals.wav`, `drums.wav`, `bass.wav`, `other.wav`, the same length as the decoded input.
  16-bit PCM with TPDF dither by default (deterministic: the same input gives the same bytes), or
  32-bit float with `--float32`. Files are written under a temporary name and renamed on success.
- `--model`: a local `.mlmodelc`, `.mlpackage`, or the release `.zip` (checked and compiled into
  the cache) instead of the download.

Python: `separate(input_path, out_dir, *, model_path=None, device="gpu", overlap=0.25,
float32=False, progress=None)` returns `{"vocals": Path, ...}`. `progress(stage, fraction)` is
called for `"download"`, `"load"`, `"read"` and `"separate"`. `separate_source(source, out_dir,
predict)` takes any object with a re-iterable `blocks()` and any `predict(spectrum)` function, for
use without ffmpeg or with another runtime.

## Tests

```sh
python3 -m venv .venv && .venv/bin/pip install -e '.[test]' && .venv/bin/python -m pytest
```

The tests use synthetic signals only and do not need the model: a pass-through network stands in
for Core ML. A real-model test runs when the model is already cached (or `SCNET_STREAM_MODEL`
points at it), and a PyTorch cross-check of the STFT runs when torch is installed.
